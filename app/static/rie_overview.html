§3 — System workflow

Three independent workflows.

Automated analysis, manual review, and rule activation are deliberately separated. That separation is the product promise: a machine can suggest, only a person can approve, and only an administrator can make a rule live.

🔍

Feedback Analysis

§3.1

Automated. Validates, classifies, extracts, and checks every submission before a human ever sees it.

  • Input + auth + workspace validation
  • 7-stage pipeline (below)
  • Returns Suggestion ID + evidence
Ends after review routing — no rule created.
👁

Human Review

§3.2

People decide. Reviewers inspect the evidence and choose the outcome.

  • Approve / Reject / Clarify / Archive
  • Every decision audited
  • Approval ≠ creation or activation
Original feedback stays immutable.
🚀

Rule Creation & Activation

§3.3

Administrators deploy. Approved suggestions become draft rules, then — explicitly — active ones.

  • Draft created only from APPROVED
  • Validated vs. rule repository
  • Admin activates → ACTIVE + live
No silent promotion from AI to production.
§3.1 — Feedback Analysis Flow

From free text to structured evidence.

Each submission is validated, traced with a Feedback ID, and passed through a sequential pipeline. Every stage produces its own output — nothing is inferred or invented.

Pipeline — 7 stages

1 Classification 2 Rule Extraction 3 Duplicate Detection 4 Conflict Detection 5 Clarification 6 Confidence & Evidence 7 Review Routing
After routing the API returns a Suggestion ID, status, and all evidence. The analysis workflow ends — no rule is touched.
1

Feedback Classification · what we understood

Predicts the feedback type, rule category, business domain, actionability, whether clarification is needed, and the initial priority — the shared context for everything that follows.

feedback typerule categorybusiness domainactionabilitypriority
2

Rule Extraction · turning words into structure

Converts unstructured feedback into one or more canonical business rules — term, operation, conditions, scope, time window, threshold, affected tables/columns and schema references. One submission can yield multiple rules, each stored independently and traceable to its Feedback ID.

Extracted
  • Business term & operation
  • Conditions (field · operator · value)
  • Scope · time window · threshold
  • Affected tables / columns
Validation
  • Every field checked vs. schema
  • Unknown tables/columns flagged
  • Invalid terms/operations rejected
  • Nothing invented, nothing assumed
3

Duplicate Detection · have we seen this?

Compares the suggestion to approved rules and prior suggestions. Retrieval uses pgvector semantic search; the decision is structured — term, operation, conditions, scope, time window, threshold, affected schema — recorded per rule.

exact duplicatesemantic duplicateextensionmodificationunrelated
4

Conflict Detection · will it break something?

Evaluates whether the proposal logically conflicts with active rules — same two-stage pattern: semantic retrieval, then structured comparison. Results are recorded independently and feed the routing decision.

direct conflictpotential conflictno conflict
5

Clarification Handling · when something's missing

If mandatory information is missing or ambiguous, a structured clarification request is generated. The system never invents data. Requests are stored separately; when answered, a new Analysis Run is created from original + response — the original submission stays immutable.

6

Confidence & Evidence · explainability first

Each stage emits its own evidence — calibrated classification/extraction probabilities, schema validation (pass / fail + coverage, not a score), duplicate/conflict results — all recorded separately to support review.

7

Review Routing · who should look?

Decides the review path from all prior evidence. Any of these forces mandatory manual review: schema failure, missing mandatory fields, sensitive rules, duplicate/conflict signals, or model confidence below threshold.

normal reviewhigh-priority reviewclarification requiredvalidation failuremandatory manual review
§3.2 — Human Review Flow

People decide. Every time.

Reviewers work from a dedicated dashboard. The original feedback, the structured suggestion, and all evidence are presented together — duplicates, conflicts, schema checks, and any clarification requests.

📋

What reviewers see

Everything from the pipeline, in one place

  • 💬 Original business feedback
  • 🧩 Structured rule suggestion + extracted entities
  • 🏷 Classification & priority
  • 📐 Schema validation result + coverage
  • 🔍 Duplicate & conflict findings
  • 📊 Confidence scores & supporting evidence
  • ❓ Clarification requests (if any)
✅

What reviewers do

One explicit action — fully audited

After evaluation, a reviewer takes exactly one action. Each is logged with reviewer identity, decision, timestamp, and comments. Approval only marks APPROVED — it does not create or activate a rule.

✓ Approve ✕ Reject ❓ Request clarification 🗄 Archive

Clarification? The original feedback is untouched — the request/response are stored separately and a new Analysis Run is created from both, preserving a complete audit trail.

§3.3 — Rule Creation & Activation

From approved to live — deliberately.

Creation and activation are intentionally separate. Reviewer approval does not create a rule; an administrator must explicitly activate it. This two-gate design is what prevents unintended deployment of AI-generated logic.
