# V4 User Journey: Workflows & Integrations

## Introduction
The Rule Intelligence Engine is predominantly interfaced via upstream REST APIs. While end-users interact with a User Interface (UI), the underlying journey mapped across our systems tracks structured payloads across distinct operational boundaries.

Below is the structured flow of how a user journeys through the primary actions the engine supports.

---

## 1. The Analyst Journey (Extracting Rules)

**Objective**: Convert ambiguous conversational text from business users into concrete software logic.

### Step 1: Inbound Sourcing
The User submits text via their external CRM or chat window (e.g., *"Make sure the VIP discount is 20% on hats."*).
- System tracks this as a `Feedback` log attached to their `workspace_id`.
- An `AnalysisRun` drops the request onto the processing loop.

### Step 2: Automated Clarifications (The Bot Pushback)
Often, business requests are poorly structured. 
- The Rule Engine spots a missing parameter (e.g., *"What qualifies as VIP?"*).
- The Engine initiates a `POST /v1/clarifications` request and loops back to the user via UI prompts.
- The user inputs the answer, submitting it to the `POST /v1/clarifications/{id}/respond` endpoint.
- Once completely answered, the analysis resumes autonomously.

### Step 3: Suggestion Presentation
The final, parsed algorithmic structure is saved.
- The user accesses a dashboard hitting `GET /v1/suggestions`.
- They read the formatted, strict JSON rule proposed by the Engine (e.g., `{"operation": "apply_discount", "value": "20%", "product": "hats"}`).

---

## 2. The QA / Manager Journey (Governance)

**Objective**: Ensure that no AI-generated code is ever unilaterally pushed into the canonical rule-base without oversight.

### Step 1: Review Assignment
- QA managers hit the `POST /v1/reviews` APIs allocating `Suggestion` IDs generated by the Analysts to specific developer tags.
- The UI filters queues by hitting `GET /v1/suggestions?status=pending_review`.

### Step 2: Conflict Adjudication
- If the system detects a conflict (e.g., an older rule says *"VIP is 10%"*), a red flag is displayed against the suggestion in the manager's UI loop.
- The Manager adjudicates. 

### Step 3: Final Disposition
- The Manager interfaces with the payload clicking ✅ **Approve** or ❌ **Reject**.
- This dispatches commands to the `SuggestionLifecycleService` (`POST /v1/suggestions/.../approve`).
- If approved, the canonical Rule is deployed operationally and timestamped heavily in the Audit logs for non-repudiation.

---

## 3. The ML Operations Journey (Benchmarking)

**Objective**: Ensure prompt improvements and LLM upgrades don't cause regressions.

### Step 1: Creating Submissions
- Data Engineers load synthetic scenarios (`DatasetVersion`) and a new model artifact (`ModelVersion`).

### Step 2: Asynchronous Trigger
- The engineer submits `POST /v1/evaluations`. 
- Since waiting for 5,000 dataset samples to run through an LLM across the network would time out an HTTP connection drastically, the API assigns it a UUID and immediately returns a queue receipt (`"status": "pending"`).

### Step 3: Resolution Polling
- The engineer builds a script polling `GET /v1/evaluations/{id}` every 5 minutes.
- Once the background Celery Workers exhaust the Redis Queue tasks, the API response populates a list of `metrics` containing `F1 Score`, `Accuracy`, or `Latency` metrics compared directly against the determinism benchmarks.
